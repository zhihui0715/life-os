# Database Schema & Migration Plan

Status: **Draft for Stage 1** · Database: PostgreSQL 16 · ORM: SQLAlchemy 2.x · Migrations: Alembic (via Flask-Migrate)

This document is the source of truth for table design. When a migration changes a table, update this file in the same commit.

---

## 1. Conventions (apply to every table unless stated)

| Rule | Detail | Why (beginner note) |
|---|---|---|
| Primary key | `id UUID` — generated by the client *or* server (`uuid4`) | Offline PWA can create records before the server sees them |
| Ownership | `user_id UUID NOT NULL → users.id ON DELETE RESTRICT` | Every query filters by user; prevents data leaking between accounts later |
| Timestamps | `created_at`, `updated_at` as `timestamptz NOT NULL DEFAULT now()` | `timestamptz` stores an exact instant (UTC); safe to compare |
| Archiving | `archived_at timestamptz NULL` on long-lived entities | "Archived" = hidden, never lost |
| Deletion | Foreign keys to *history* use `RESTRICT` or `SET NULL`. `CASCADE` only for rows meaningless without the parent (marked 🔗) | Prevents one delete from silently wiping personal history |
| Calendar days | `date` columns, interpreted in the user's timezone (default `Asia/Kuala_Lumpur`) | "Did I do my habit on 20 Oct?" is a *local day*, not a UTC instant |
| Text limits | Titles `varchar(200)`; long text `text` (validated to 20 000 chars by the API) | Guards against accidental huge payloads |
| Enums | Stored as `varchar` + `CHECK` constraint, not native PG enums | Adding a value later is a simple migration |
| Naming | snake_case, plural table names, FK = `<singular>_id` | Consistency |
| Indexes | Always on `(user_id, …)` for the main list query of each table | Fast filtered lists |

### 2.3 Goals

**goals**
| Column | Type | Notes |
|---|---|---|
| id, user_id | uuid | |
| title | varchar(200) | NOT NULL |
| description | text | |
| category_id | uuid | FK SET NULL |
| horizon | varchar(10) | `'short'` \| `'long'` |
| status | varchar(12) | `'active'` \| `'completed'` \| `'abandoned'` \| `'paused'` |
| success_criteria | text | free text: what "done" means |
| progress_mode | varchar(12) | `'milestones'` \| `'tasks'` \| `'manual'` — how % is computed |
| manual_progress | smallint | 0–100, used only when mode = manual |
| start_date, target_date | date | target_date ≥ start_date (CHECK) |
| completed_at, archived_at | timestamptz | CHECK: `(status = 'completed') = (completed_at IS NOT NULL)` |
Index: `(user_id, status)`. Default `progress_mode` is `'tasks'`.

**Progress rules** (implemented in `backend/app/modules/goals/service.py`, explained in the app next to the number):
- `tasks`: completed linked tasks ÷ linked tasks. Archived tasks that were never completed are left out (dropped work doesn't count against you); completed ones always count. Subtasks never count (only their parent can link to a goal).
- `milestones`: completed milestone weight ÷ total milestone weight.
- `manual`: the last value the user set.
- Nothing to measure (no linked tasks / no milestones / no value) → progress is `null` ("No data yet"), never 0%.

**goal_milestones** (🔗 CASCADE from goal is *not* used — RESTRICT; milestones are history)
| Column | Type | Notes |
|---|---|---|
| id, user_id, goal_id | uuid | goal FK RESTRICT |
| title | varchar(200) | |
| position | integer | ordering |
| weight | smallint | default 1; for weighted milestone progress |
| target_date | date | |
| completed_at | timestamptz | NULL = open |

**goal_progress_updates** — the goal's history timeline
`id, user_id, goal_id (RESTRICT), kind, progress smallint 0–100 NULL, status NULL, note text NULL, created_at`.
`kind`: `auto` (calculated progress moved — written whenever a task/milestone change shifts the number), `manual` (user set a value), `note` (free note), `status` (goal status changed). Index `(goal_id, created_at)`.

### 2.4 Tasks

**tasks**
| Column | Type | Notes |
|---|---|---|
| id, user_id | uuid | |
| title | varchar(200) | NOT NULL |
| notes | text | |
| status | varchar(12) | `'inbox'` \| `'todo'` \| `'in_progress'` \| `'done'` |
| priority | smallint | 1 (urgent) … 4 (low), default 3 |
| due_date | date | soft target day |
| deadline | timestamptz | hard deadline, optional |
| estimate_minutes | integer | ≥ 0 |
| actual_minutes_manual | integer | user override; NULL = derive from focus sessions + activity logs |
| parent_task_id | uuid | FK RESTRICT. Subtasks are one level deep; a task with subtasks can't become a subtask; a parent with subtasks can't be deleted (all enforced by the API) |
| goal_id | uuid | FK SET NULL. Not allowed on subtasks (link the parent) so goal progress never double-counts |
| milestone_id | uuid | FK SET NULL; must belong to `goal_id`. Choosing a milestone fills in its goal; changing the goal clears a milestone from the old goal |
| category_id | uuid | FK SET NULL |
| position | integer | manual ordering in lists |
| completed_at | timestamptz | set when status → done, cleared on reopen |
| archived_at | timestamptz | |
CHECK: `(status = 'done') = (completed_at IS NOT NULL)`.
Indexes: `(user_id, status, due_date)`, `(goal_id)`, `(milestone_id)`, `(parent_task_id)`.
List views show top-level tasks only (with `subtasks_done/subtasks_total`); `?parent_id=` lists a task's subtasks; search (`?q=`) covers subtasks too.
**Search** is a case-insensitive substring match (`ILIKE`) on title and notes, with `%`/`_` escaped. It works for Chinese without word segmentation. No search index yet — fine for one person's data; add a `pg_trgm` index if it ever gets slow.

> **Deadline vs. due date vs. scheduled time**: `due_date` = "I aim to finish this day"; `deadline` = "it must be done by this instant"; scheduled time lives in `schedule_events` (a task can have zero, one or several time blocks).

### 2.5 Calendar

**schedule_events**
| Column | Type | Notes |
|---|---|---|
| id, user_id | uuid | |
| title | varchar(200) | |
| description | text | |
| kind | varchar(12) | `'appointment'` (hard) \| `'task_block'` \| `'preference'` (soft, e.g. preferred study hours) |
| is_hard | boolean | default true for appointment, false for task_block; always false for preference |
| all_day | boolean | |
| starts_at, ends_at | timestamptz | CHECK ends_at > starts_at; for all-day events, local midnight → next local midnight |
| tzid | varchar(64) | timezone the event was created in (needed to expand recurrences correctly) |
| rrule | varchar(300) | RFC 5545 RRULE, NULL = single event. Allowed: DAILY/WEEKLY/MONTHLY/YEARLY, COUNT ≤ 1000 or UNTIL (not both), no DTSTART |
| recurrence_until | timestamptz | denormalised end of series, NULL = infinite (for fast range queries) |
| task_id | uuid | FK SET NULL. Required when kind = task_block (CHECK); must be a top-level task |
| category_id | uuid | FK SET NULL |
| archived_at | timestamptz | deleting an event = archive |
Index: `(user_id, starts_at)`, `(user_id, recurrence_until)`, `(task_id)`.

**event_exceptions** (🔗 CASCADE from event)
`id, event_id, original_start timestamptz, is_cancelled boolean, override_starts_at, override_ends_at, override_title`. UNIQUE (event_id, original_start). CHECK: cancelled, or both override times set with end > start.

**user_settings — added in 0005:** `score_weights` jsonb (`{"tasks":30,"goals_learning":25,"habits":30,"wellbeing":15,"enabled":{…}}`, NULL = defaults; 0–100 each, at least one enabled with weight > 0), `weekly_learning_target_min` int (NULL = no target), `dashboard_layout` jsonb (ordered `[{key, visible}]`; sections added in later versions are appended automatically).

**user_settings.working_hours** (jsonb, added in 0003): `{"mon": [["09:00","18:00"]], …}`, up to 3 non-overlapping ranges per day; NULL = default Mon–Fri 09:00–18:00, Sat–Sun 10:00–16:00.

**Calendar rules** (code: `backend/app/modules/calendar/`):
- Recurrences are expanded on read in the event's own timezone using wall-clock times, so a 09:00 class stays at 09:00 across daylight-saving changes (tested with America/New_York).
- Edit scopes: "this occurrence" (writes an exception) or "all" (edits the series). Changing a series' time or rule drops its single-occurrence changes; the API returns how many (`dropped_exceptions`) and the app warns first. "This and following" is not supported yet.
- Busy time = timed appointments + task blocks. Preference windows and all-day events are never busy.
- Conflicts: overlapping busy occurrences; `hard` when both are fixed. Only a flexible task block is ever offered a move, to the next free slot that fits.
- Free time = working hours − busy time, from now on.
- Workload / at risk (next 14 days): open top-level tasks with an estimate; remaining = estimate − blocked time before the deadline (or end of due date); `at_risk` when remaining > free time before then.
- Suggestions: free slots before the task is due (or within 7 days), preferring preference windows, then earliest; blocks ≤ 3 h; no estimate → assume 1 h and say so.
- Nothing in conflicts/free-slots/suggestions writes data. Moves and new blocks happen only after a confirm dialog; dragging also asks first and snaps back if you cancel.

### 2.6 Habits (built in Stage 4, migration 0004)

**habits** — `id, user_id, name varchar(120), description, category_id (SET NULL), goal_id (SET NULL), target_value numeric(10,2), target_unit varchar(20), start_date date, archived_at`.
The schedule is **not** a column on habits: it lives only in `habit_schedule_changes`, so there is one source of truth.

**habit_schedule_changes** (🔗 CASCADE with habit) — `id, habit_id, effective_from date, schedule_type ('daily'|'weekdays'|'x_per_week'), weekday_mask (Mon=1 … Sun=64), times_per_week (1–7)`. UNIQUE (habit_id, effective_from). The first row is written at creation (effective from the start date); a schedule edit adds a row effective **today**, so past days are always judged by the schedule in force then. Unused fields hold neutral values (mask 127, times 7).

**habit_logs** (RESTRICT — history) — `id, user_id, habit_id, log_date (UNIQUE per habit), state ('done'|'skipped'), value, note`.
"Missed" is **not stored**: it's a scheduled past day with no log, so correcting history is just adding/removing a log. No check-ins for future days or before the start date.

**Streak rules** (`backend/app/modules/habits/streaks.py`, pure functions with 11 unit tests, shown in the app):
- Only scheduled days count. `done` extends the streak; `skipped` is a rest day (neither extends nor breaks); a missed day resets it. The best streak is kept.
- Today is never missed until it's over. Check-ins on unscheduled days are kept as extras and don't affect the streak.
- `x_per_week` habits count in weeks (week start from Settings): a week is met when done ≥ target; the current week can only help.
- Consistency: last 30 days done ÷ (scheduled − skipped), today excluded unless logged; weekly habits: share of the last 4 completed weeks met. No eligible days → `null` ("not enough data"), never 0%.

### 2.7 Activity, focus, journal (built in Stage 4)

**activity_logs** — `title, category_id, log_date (local day), started_at, ended_at (optional), duration_minutes (1–1440, CHECK), notes, outcome, goal_id, task_id, focus_session_id (UNIQUE, SET NULL)`. Index `(user_id, log_date)`.
If both times are given the duration is calculated (a different `duration_minutes` is rejected). Nothing is recorded automatically. Learning time = logs whose category kind is `learning`. A task's `tracked_minutes` = sum of its activity logs.

**focus_sessions** — `task_id, label, planned_minutes (1–240), break_minutes, started_at, paused_at, paused_seconds, ended_at, actual_minutes, state ('running'|'paused'|'completed'|'interrupted')`. CHECKs: open ⇔ no `ended_at`; paused ⇔ `paused_at` set.
Rules: the server keeps the clock (refresh/devices don't lose it); focused time excludes pauses; **completed** when ≥ 80% of planned or marked complete, else **interrupted** (minutes still count). Stopping with ≥ 1 minute creates exactly one linked activity log; correcting the minutes updates (or removes, at 0) that log. One open session at a time.

**journal_entries** — `entry_date (UNIQUE per user), body, went_well, to_improve, challenges, lessons, gratitude, tomorrow_priorities, mood (1–5), energy (1–5)`. All optional; clearing every field deletes the row. Writing for tomorrow is allowed (priorities), further ahead is not. The Home mood check-in writes to today's entry. Journal text is never logged (tested).

### 2.8 AI (Stage 7)

**ai_runs** — `id, user_id, kind ('daily_plan'|'weekly_review'|'suggestion'), data_categories_sent jsonb, provider, model, input_tokens, output_tokens, response jsonb, status, created_at`. Raw prompts are **not** stored (they may contain journal text).

### 2.9 Insights (Stage 5, read-only — no tables)

All formulas live in `backend/app/modules/insights/metrics.py` (docstring) and are shown next to each number in the app. Key rules:
- Periods are local weeks (Settings' week start) or months; only days up to today count; "in progress" is shown.
- Missing data is `null` ("No data"), never 0: no tasks due, no scheduled habit days, no learning target and no judgeable goal, fewer than 3 mood days.
- Life Balance Score = Σ weight × component ÷ Σ weight over enabled components with data; coverage = share of enabled weight with data. Each behaviour feeds one component only.
- Goals count toward "on track" only once some of their time has passed (a goal created today is not 100% or 0%, it's left out).
- Tests compare results with hand-worked numbers and with raw SQL (time allocation).

## 3. Deletion & archiving matrix

| Entity | User action "delete" | Hard delete allowed? |
|---|---|---|
| Task, goal, habit, event, category | Archive (restorable) | Only when it has no history (e.g. a task never completed, no logs, no subtasks) — API checks, then asks for confirmation |
| Habit log, activity log, focus session, journal entry | True delete after confirmation (these *are* the corrections) | Yes |
| Milestone | Delete only if no linked tasks; else archive via goal | Conditional |
| User | Not exposed in P0 (export first) | — |

## 4. Migration plan

1. **Stage 1 migration `0001_foundation`** ✅ written: users, user_settings (locale, timezone, week_start, theme only), auth_sessions, categories, tasks (without goal/milestone/parent links).
2. **Stage 2 `0002_goals_tags`** ✅: goals, goal_milestones, goal_progress_updates, tags, task_tags; add `goal_id`, `milestone_id`, `parent_task_id` to tasks. (Autogenerated, then reviewed.)
   Remaining `user_settings` columns (working hours, score weights, learning target, dashboard layout, AI settings) are added in the stage that first uses them.
3. **Stage 3 `0003_calendar`** ✅: schedule_events, event_exceptions, user_settings.working_hours. (Autogenerated, then reviewed.)
4. **Stage 4 `0004_tracking`** ✅: habits, habit_schedule_changes, habit_logs, activity_logs, focus_sessions, journal_entries. (Autogenerated, then reviewed.)
5. **Stage 5 `0005_insights_settings`** ✅: score_weights, weekly_learning_target_min, dashboard_layout on user_settings.
6. **Stage 7 `0006_ai`**: ai_runs.

Rules:
- One migration per stage minimum; never edit a migration after it has been applied to real data — write a new one.
- Every migration has a working `downgrade()` and is tested in CI: `upgrade head → downgrade base → upgrade head` on an empty database.
- Before applying a migration to a database containing real data: run the export (Stage 6+) or `pg_dump` first.
